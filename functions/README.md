# Cloud Functions — سجل التدقيق + مزامنة Monday.com

هذا المجلد يحتوي دالتين سحابيتين مستقلتين:

1. `mirrorOpportunityAuditLog` (`index.js`) — تكتب سجل تدقيق حقيقي وغير قابل للتلاعب في مجموعة `oppAuditLog`، بديلاً عن الكتابة السابقة من العميل مباشرة.
2. `processMondayTaskQueue` (`monday-sync.js`، مُصدَّرة أيضاً من `index.js`) — تعالج قائمة انتظار مزامنة المهام مع Monday.com (`mondayTaskQueue`). راجع قسم **تكامل Monday.com** أسفل هذا الملف لتفاصيلها الكاملة.

## لماذا هذه الدالة ضرورية

قبل هذه المرحلة، كانت قواعد Firestore (`firestore.rules`) تسمح لأي عميل مصرَّح له بالكتابة المباشرة على `oppAuditLog`. هذا يعني أن "سجل التدقيق" كان يكتبه نفس الطرف الذي يُفترض أن يُراقَب — لا قيمة إثباتية حقيقية لسجل يستطيع الفاعل نفسه كتابته أو تعديله.

القاعدة الآن:

```
match /oppAuditLog/{id} {
  allow read: if isAuthorized();
  allow write: if false;   // لا كتابة عميل نهائياً — ولا حتى الأدمن
}
```

الكتابة الوحيدة الممكنة هي من هذه الدالة، التي تعمل بصلاحيات **Admin SDK** — تتجاوز Security Rules بتصميم Firebase نفسه. هذا هو "الخادم الموثوق" في السلسلة:

```
User → Application → Server Function → Immutable Audit Event
```

الدالة مُفعَّلة عبر `onDocumentWritten('opportunities/{oppId}')` — أي تعديل، إنشاء، أو حذف على أي وثيقة فرصة يُنتج تلقائياً سجل تدقيق مقابل، بصرف النظر عن الطريق الذي وصل عبره التعديل (الواجهة، سكربت مستقبلي، استيراد بيانات).

## متطلبات النشر (يجب أن تقوم بها أنت بنفسك)

**لا يمكن لـ Claude نشر هذه الدالة نيابةً عنك** — لا صلاحية وصول لحساب Firebase الحقيقي لديك من هذه البيئة. الكود مكتمل ومُختبَر بنيوياً (`node --check`، واختبار مباشر لمنطق `deepDiff`/`fieldLabel` عبر `_internal`)، لكن النشر الفعلي خطوات يجب تنفيذها من جهازك:

1. **خطة Blaze إلزامية.** Cloud Functions من الجيل الثاني (v2 — `onDocumentWritten`) لا تعمل على خطة Spark المجانية. من Firebase Console: Settings → Usage and billing → ترقية إلى Blaze. التكلفة المتوقعة لصندوق عقاري بحجم استخدام معتاد (عشرات-مئات الفرص، تعديلات يومية محدودة) ضئيلة جداً — عادة ضِمن الحد المجاني لخطة Blaze نفسه (أول ٢ مليون استدعاء شهرياً، ٤٠٠ ألف GB-ثانية).

2. **Firebase CLI:**
   ```bash
   npm install -g firebase-tools   # لو غير مُثبَّتة
   firebase login
   firebase use real-estate-ledger-f85a6   # أو معرّف مشروعك الفعلي من .firebaserc
   ```

3. **تثبيت الاعتماديات ثم النشر** (من جذر المستودع):
   ```bash
   cd functions
   npm install
   cd ..
   firebase deploy --only functions
   ```
   (أو `firebase deploy --only firestore:rules,functions` لنشر قواعد Firestore الجديدة والدالة معاً في أمر واحد — **يجب** نشر القواعد الجديدة قبل أو مع الدالة، وإلا سيستمر العميل بالمحاولة الفاشلة للكتابة على `oppAuditLog` بالقاعدة القديمة المخزَّنة سابقاً.)

4. **تحقّق من النشر:** من Firebase Console → Functions، يجب أن تظهر `mirrorOpportunityAuditLog` بحالة "Deployed". أول تعديل حقيقي على أي فرصة بعد النشر يجب أن يُنتج مستنداً جديداً في مجموعة `oppAuditLog` (يمكن مراقبته من Firestore Console مباشرة، أو من قسم "سجل التعديلات" في شاشة تفاصيل أي فرصة داخل التطبيق نفسه).

## ملاحظة تصميم مهمة: من أين تُقرأ هوية "من عدَّل"؟

الدالة تقرأ `meta.updatedBy`/`meta.createdBy` من وثيقة الفرصة نفسها لتحديد الفاعل. هذا الحقل محمي في `firestore.rules` بقاعدة `attributionHonest()` التي تفرض تطابقه دائماً مع بريد المستخدم المصادَق عليه فعلياً (`request.auth.token.email`) وقت الكتابة — فلا يمكن لعميل تزييف هوية "مَن غيَّر ماذا"، وهذا ما يجعل الاعتماد عليه من دالة خادم موثوقة آمناً ومنطقياً.

## ماذا لو لم تنشر هذه الدالة؟

التطبيق يستمر بالعمل بشكل طبيعي تماماً — لا يعتمد أي جزء آخر من النظام على هذه الدالة وظيفياً. الأثر الوحيد: قسم "سجل التعديلات" (Version History) في شاشة تفاصيل كل فرصة سيبقى **فارغاً لكل تعديل جديد** بعد نشر `firestore.rules` المحدَّثة (لأن الكتابة من العميل أصبحت مرفوضة بتصميم، ولا يوجد بديل يكتب محلّها بعد). في وضع الديمو/المحلي (`core.DEMO_MODE`) لا تتأثر تجربة السجل بأي حال — الكتابة المحلية هناك تعمل كما كانت دائماً (انظر التعليق في `src/features/audit-trail.js`).

## تزامن منطق الفرق (deepDiff) مع العميل

منطق `deepDiff`/`fieldLabel`/`FIELD_LABELS`/`IGNORE_PATHS` هنا **منقول يدوياً** من `src/features/audit-trail.js` (لا مستورَد — بيئتان منفصلتان تماماً: Node CommonJS هنا، ES module في متصفح العميل هناك، بلا أداة بناء مشتركة بينهما في هذا المشروع). أي تعديل مستقبلي على قواعد الفرق نفسها (حقول تُتجاهَل، طريقة مقارنة المصفوفات، تسميات حقول جديدة) **يجب تطبيقه في الملفين معاً** — وقد تُرك تعليق بالمثل في كل ملف يشير للآخر.

## تكامل Monday.com (`monday-sync.js` — `processMondayTaskQueue`)

### السياق والطلب

طلب المستخدم ربط Monday.com بالتطبيق بحيث:
- مساحة عمل Monday (`https://opal3ks-team-company.monday.com`) مرتبطة بحساب تسجيل الدخول `opal3k@gmail.com` (نفس أول بريد أدمن في هذا التطبيق، `core.ADMIN_EMAILS[0]`).
- ملف مستخدم Monday محدَّد بدقة (`https://opal3ks-team-company.monday.com/users/115387628`) يُستخدَم كـ"مالك مهام افتراضي" — بريده `saeed@opalco.sa`.
- بالإضافة إلى "لوحة صلاحيات" في Monday تعكس نظام الأدوار الحالي في التطبيق (`src/features/roles-permissions.js`).

### الحاجز الفعلي (Blocker) — لماذا لا توجد مزامنة حيّة الآن

هذا التطبيق صفحة ثابتة بالكامل (Static SPA تعمل من متصفح العميل مباشرة + Firestore)، بلا أي خادم HTTP خاص بها غير Cloud Functions المذكورة أعلاه. أي اتصال حقيقي بـ Monday.com API (GraphQL، `https://api.monday.com/v2`) يتطلب **رمز مصادقة حقيقياً** — إما:

- **Personal API Token** من حساب Monday.com نفسه (Avatar → Admin → API، أو من إعدادات المطوّر الشخصية)، أو
- **تسجيل تطبيق OAuth** كامل (Client ID/Secret) إن أردتم تدفق تفويض متعدد المستخدمين.

**لا يوجد أي منهما في هذا المستودع، ولا يمكن لأي كود توليدهما أو افتراضهما** — وهذا تحديداً الحاجز الذي يمنع أي مزامنة فعلية اليوم. لا يمكن أيضاً وضع مثل هذا الرمز في أي كود عميل (`src/`) أو أي مستند Firestore عادي، لأن أي قيمة تصل لمتصفح العميل تصبح قابلة للقراءة من أي شخص يفتح أدوات المطوّر، بصرف النظر عن صلاحيات حسابه داخل التطبيق.

### الحل المُنفَّذ (آمن، جاهز للتفعيل لاحقاً بلا إعادة كتابة)

| الطبقة | أين | ماذا تفعل |
|---|---|---|
| العميل | `src/features/monday-integration.js` | لوحة إعداد للأدمن فقط (بلا أي حقل رمز API)، وزر "إرسال إلى قائمة انتظار Monday" داخل كل فرصة (لمدير صندوق فأعلى) يكتب طلب مزامنة بحالة `pending` في `mondayTaskQueue` — **لا اتصال مباشر بـ Monday.com من المتصفح إطلاقاً**. |
| القواعد | `../firestore.rules` | `mondayConfig` (قراءة لأي عضو مصرَّح له، كتابة للأدمن فقط، بلا أي حقل سرّي فيها أصلاً)، و`mondayTaskQueue` (قراءة للجميع، إنشاء لمدير صندوق فأعلى بشرط نزاهة الناشر وحالة `pending` فقط، **تعديل/حذف ممنوعان بالكامل من العميل** — نفس فلسفة `oppAuditLog`). |
| الخادم | `monday-sync.js` (هذا المجلد) | `processMondayTaskQueue`، تُشغَّل تلقائياً عند إنشاء أي وثيقة في `mondayTaskQueue`. تقرأ `MONDAY_API_TOKEN` من Secret Manager عبر `defineSecret()` — لا من أي كود أو Firestore. |

### ماذا تفعل الدالة بالضبط

1. **لو `MONDAY_API_TOKEN` غير مُعدّ بعد** (وهذا وضعها الحالي — لم يُضبَط أي سر): تُحدِّث حالة الطلب إلى `blocked_missing_secret` مع رسالة توضيحية، وتسجّل تحذيراً في Cloud Logging. **لا محاولة اتصال، ولا رمز وهمي.**
2. **لو السر مُعدّ لكن لا يوجد معرّف لوحة Monday** (لا في الطلب نفسه ولا في `mondayConfig/settings`): تُحدِّث الحالة إلى `blocked_missing_board`.
3. **لو الاثنان متوفران**: تُرسِل فعلياً `mutation create_item` إلى `https://api.monday.com/v2` (توثيق `Authorization: <token>`)، وتُحدِّث الحالة إلى `synced` (مع `mondayItemId`) أو `failed` (مع رسالة الخطأ الفعلية).

### خطوات التفعيل الكاملة (تتطلب صلاحيتك أنت — لا يمكن لأي جلسة مساعد تنفيذها نيابة عنك)

1. **من حساب Monday.com** (`opal3k@gmail.com`، مساحة العمل `opal3ks-team-company`): أنشئ Personal API Token حقيقياً (Avatar الشخصي → Admin → API، أو Developers → My Access Tokens)، وحدِّد معرّفَي لوحتي "المهام" و"الصلاحيات" الفعليين في Monday (رقم اللوحة يظهر في رابط اللوحة نفسها في المتصفح).
2. **من جهازك، بصلاحية مالك/محرِّر على مشروع Firebase** (حالياً `opal3k@gmail.com` أو `ggocss@gmail.com` فقط، حسب `.firebaserc` → `real-estate-ledger-f85a6`):
   ```bash
   firebase login
   firebase use real-estate-ledger-f85a6
   firebase functions:secrets:set MONDAY_API_TOKEN
   # الصقه عند السؤال — لن يُطلَب منك كتابته في أي واجهة أو ملف كود إطلاقاً
   ```
3. **نشر القواعد + الدوال معاً** (من جذر المستودع):
   ```bash
   cd functions && npm install && cd ..
   firebase deploy --only firestore:rules,functions
   ```
4. **من داخل التطبيق** (مسجّلاً دخول كأدمن): افتح لوحة "🔗 Monday.com" الجديدة في الشريط العلوي، وأدخل معرّفَي اللوحتين اللذين حصلت عليهما في الخطوة ١. لا تحتاج لكتابة أي رمز API هنا — الحقل غير موجود أصلاً.
5. **إن أردت أن يدير `saeed@opalco.sa` هذه اللوحة بنفسه من داخل التطبيق مستقبلاً**: هذا قرار منفصل يخص هذا المشروع تحديداً (لا علاقة له بـ Monday.com) — يتطلب إضافته أولاً كعضو فريق حقيقي عبر "👥 إدارة الفريق" (يحتاج حساب Firebase Authentication فعلي له)، ثم تعيين دوره كـ"مدير صندوق" أو "أدمن" من لوحة "🛡️ الأدوار والصلاحيات". لم يُنفَّذ هذا تلقائياً هنا لأنه قرار وصول/هوية حقيقي يخص حسابك، لا إعداد تكامل.

### ماذا لو لم تُفعَّل هذه الخطوات؟

التطبيق يعمل بشكل طبيعي تماماً بدونها. زر "إرسال إلى قائمة انتظار Monday" يستمر بكتابة طلبات في `mondayTaskQueue` (مرئية في لوحة "🔗 Monday.com")، لكنها تبقى بحالة `blocked_missing_secret` حتى تُنفَّذ الخطوات أعلاه — لا فقدان بيانات، لا كسر لأي جزء آخر من التطبيق.
